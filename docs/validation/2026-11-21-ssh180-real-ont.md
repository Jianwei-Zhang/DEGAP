## 阻断性发现：ONT FASTA 错误被当成正常无结果

全部五次局部组装的 `assembler/hifiasm/hifiasm.stderr.log` 均包含：

```text
[ERROR] .../reads/ont.extensionReads.left.fa is in fasta format rather than fastq format
```

右侧文件同样报错。实际调用形式为：

```text
hifiasm -i -n 1 -o ... -t 4 --ont .../ont.extensionReads.left.fa
```

排查路径（针对测试提交）：

1. `bin/FindExtensionContigs.py` 的 `_prepareONTOnlyReads()`（约 858–905 行）禁用了原 FASTQ 恢复逻辑，直接返回筛选后的 FASTA。
2. `hifiasm()` 以 `--ont` 执行；本环境的 hifiasm 报上述格式错误，但返回 **0**。
3. 现有严格工具检查主要检查非零退出码（约 1379 行），遗漏了零退出码下的显式错误。
4. 没有产出有效组装后，代码创建空结果（约 1510 行）并转入 read-common fallback，最后发布 `no_extension_contigs` / `exhausted`。因此这些状态不能解释为“真实数据已经无路可延伸”。

这不是本轮证据所能支持的 reads 不足、双向调度失效或组装器精度结论。应先修正输入/错误传播，再评估算法成效。转换禁用逻辑早于本次双向改动；本分支的严格故障检查未补齐这个既有风险。

### 对先前合成 ONT 验收的更正

回查本地 `/tmp/degap-family-final-fixtures/test_gap_cli_ont-*/` 保留的 hifiasm stderr，发现相同错误。原 CLI 测试能精确拼接合成序列，是因为 fallback 仍能连接，并不证明 ONT hifiasm 组装成功。

因此，先前“真实工具执行并得到正确序列”的证据只能说明工具调用及端到端结果；**ONT 组装阶段成功这一更强结论应撤回**。测试需要断言实际有效组装产物及无显式工具错误，不能仅检查 CLI exit 0 和最终闭合。
